# vibe Coding Harness 工具
## Git
- head 指针
指向当前所在的分支，所在的版本
git reset --hard <版本号>
          --soft
回退到历史的任意版本
-- hard 丢弃目前的修改，直奔那个版本，仓库是干净的
-- soft 不会丢弃工作区的修改，会走到那个版本进入暂存区之前，生成的局部修改text，title
 git restore --staged <文件>
 会将暂存区的修改恢复到工作区
 git checkout -- <文件>
 丢掉工作区的修改


## Vibe Coding 开发前的步骤和关键点
通过vibe coding，项目推进特别快，但是越往后代码越乱，慢慢变成屎山代码，越改越差，最后整个项目崩盘

问题不在于ai的强弱，在于vibe coding 它不是把这个活直接丢给ai，就可以直接完成项目，而是你还要构建一套工程流程，去驾驭AI，这就是Harness Engineering
前端工程化是Vite

## Vibe Coding 标准工作流
### 开发前的九个步骤
规划就是一切
#### 三个阶段
- 第一个阶段叫做定图纸
1. 先别去生成代码，先去导入需求
先把痛点解决掉，把目标用户，使用场景，和你理想中的核心功能，全部讲给ai，不用追求严谨，信息量，定完需求
2. 定完这个需求后，把这个需求整理成一个PRD文档，你来验收，让AI输出一份比较结构化的文档，它中间包括了功能列表，用户流程，页面清单，每个功能你都要补上一句，到底做到什么程度才算完成（边界）？
例如：登录成功，不是一句话，要说清楚，登录失败，提示什么，登录成功以后跳转到哪里（首页还是其他地方），如果没有验收标准，AI会写的越来越发散
PRD.md
3. 提前定好视觉，和页面框架
找2-3个参考网站，或者让AI去生成几种风格的方案，由我们来决定网页的布局，页面有哪些内容，整体是用简约风还是豪华风，为了不让AI一边写逻辑功能，一边去把UI推倒重来
DESING.md

- 第二个阶段打地基
1. 明确项目的边界和非功能需求
本地运行还是线上公开，用户量多少，有没有用户数据，有没有支付功能，性能和成本有没有上限。安全，性能，可用性，成本，这四个非功能性需求不写清楚，后面一定会反工
2. 锁定技术栈，越可验证越好
适合的就是最好的，React + TS + Tailwind CSS
claude.md
3. 让AI 生成轻量架构草案
目录架构怎么分层，核心模块有哪些，数据模型长什么样，有哪些组件

- 第三个阶段立好规矩
1. 固化成文档
现在的Agent和llm交互都会用一个文档，需要把PRD，设计，架构，当前状态，都写成一个项目根目录下的几个文本，固化下来，成为边界
PRD.md(产品需求文档)
ARCH.md(系统架构文档)
Project.md(当前项目文档)
DESING.md(设计文档)
这些都是AI的全局上下文，都是vibe coding的永久约束
2. 定开发规范和建参考文件夹
- 代码规范
- 错误处理
api 接口
restful 规范
可以给一个样本参考
3. 定好git和质量阀门
